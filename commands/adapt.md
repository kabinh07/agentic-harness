# /agentic-harness:adapt

For a project where planning is already complete — done by a different
agentic tool, before agentic-harness was ever installed — this reads that
tool's own output and feeds agentic-harness's execution loop
(architect/manager/test-writer, `TASKS.md`) from it, instead of walking
the native `BRD → SRS → ... → EPICS` chain. The execution loop itself is
completely unchanged by this: `/agentic-harness:architect` still segments,
delegates, and gates on independent RED→GREEN→refactor→review exactly as
it does for a natively-planned project.

This is a **read-only ingestion**. It surveys the external tool's
artifacts and mirrors only what agentic-harness's own execution layer
needs into agentic-harness's own files — it never edits, regenerates, or
otherwise touches the external tool's own artifacts.

## Known external tools

One row today; add a row here (and a matching cheat-sheet in
`agents/external-planning-analyst.md`) to support another tool later —
nothing else in this command needs to change to add one.

| Tool | Signature (any match; filesystem-only, no global-state checks) |
|---|---|
| `forge` | `pipeline/state.md` exists, OR `.forge/` exists |

Filesystem-only detection is deliberate — this project's own files
already say enough; reading global `~/.claude/plugins/...` install state
would be fragile and unnecessary.

## Precondition

An external tool must be identifiable: either detected fresh against the
signature table above, or already recorded in
`planning.external_planning.tool` from a prior run of this command or
from `/agentic-harness:init`'s own detection step. If neither applies,
stop and say so — don't guess at which tool, or invent one where none
exists.

## Steps

1. **Detect or confirm the tool.** If `planning.external_planning.tool`
   is already set, use it. Otherwise check the signature table; if
   exactly one tool matches, confirm with the user before proceeding
   (`AskUserQuestion`) rather than assuming a filesystem match is
   sufficient on its own — a false positive here would misdirect every
   later step. If none match, stop.
2. **Survey.** Dispatch `agentic-harness:external-planning-analyst`
   (Agent tool, `subagent_type: agentic-harness:external-planning-analyst`)
   with the detected tool's name and root marker. It returns Goals /
   Segments / Task backlog / Open gaps, each with evidence paths.
3. **Confirm with the user.** Present the survey's shape (goal count,
   segment count, task count, gap count) and enough detail to spot a
   misread — per `planning-protocol.md`'s Never fabricate discipline,
   this is evidence to confirm or correct, never asserted silently as
   fact. Loop on revise the same way any planning-phase stage does.
4. **Write `planning/BUSINESS_GOALS.md`** from the confirmed goals, same
   human-readable shape `/agentic-harness:configure` already produces,
   with a provenance line at the top instead of the usual "Generated by
   /agentic-harness:configure from planning/BRD.md" note — e.g. "Mirrored
   from Forge's `pipeline/01-srs/srs.md` §1.2 — do not hand-edit; re-run
   `/agentic-harness:adapt` if the source changes." (Same pattern
   `design.md`'s `DESIGN.md` already uses for its Canonical-source
   pointer.)
5. **Fill `project.config.yaml`**:
   - `project.name`/`project.description` if not already set.
   - `planning.source: external`.
   - `planning.external_planning`: `tool`, `source_artifacts` (the
     cheat-sheet paths actually used), `mapped` (`business_goals: true`,
     `segments: true`, `tasks_seeded: N`), `gaps` (every open gap from
     step 2, verbatim enough to be actionable — never summarized away).
   - `architecture.segments`: one entry per confirmed segment/component —
     `name`, `description`, `trigger`. Leave `owns_paths`, `agent`, and
     `test_command` blank, exactly like `configure.md` Step 5's existing
     "no code yet" fallback — `/agentic-harness:architect` fills those in
     the first time it runs against real code, same as any other project.
   - `manager.business_goals`: same list as `BUSINESS_GOALS.md`, kept in
     sync per the usual convention.
   - Every one of the 8 native `planning.stages.*` entries →
     `status: skipped`, with a note distinguishing this from a
     `design`/`erd`-style per-stage skip: `(external via <tool>)`.
6. **Resolve gaps before seeding tasks.** For every open gap from step 2,
   ask the user directly — "Still open (per <tool>): <gap text>. Resolved
   now, or should tasks depending on it be seeded as blocked?" Never
   decide this yourself. Record the answer.
7. **Seed `TASKS.md`** from the confirmed task backlog, existing schema
   unchanged:
   ```
   | N | <task, specifics from the external backlog> [<external-task-id> · <owning-segment-id>] | <goal> | External YYYY-MM-DD (<tool>) | 🔴/🟡/🟢 | <Sprint N or —> | ⏳ TODO | — | — | — |
   ```
   - The trace tag points at the **external** artifact's own ID —
     `[TASK-259 · SPEC-001]`, for example — never a fabricated
     `F-##`/`E-##`/`EARS-##`. This is what `architect.md` Phase 3b
     resolves back to the external tool's own acceptance-criteria text
     before dispatching `test-writer`'s RED phase — see that file's spec
     -resolution step.
   - Any task a step-6 answer marked still blocked → `⚠ BLOCKED` instead
     of `⏳ TODO`, with the gap as the recorded reason.
   - Priority derived the same way `epics.md` does today (judgment, not a
     mechanical rule) from whatever priority signal the external backlog
     states.
   - Agent column stays `—`; `/agentic-harness:architect` resolves it at
     dispatch time, same as any other project.
   - Sync via any enabled `config.tools.*` mirror skill, same as any
     other `TASKS.md` write.
8. **Update `_Last updated:`** in `TASKS.md`.

## Rules

- Never edit, regenerate, or otherwise write into the external tool's own
  artifacts (for Forge: `pipeline/`, `.forge/`, any knowledge-model
  submodule it reads from) — read-only toward them, always.
- Never invent a segment's filesystem paths, a task's status, or a gap's
  resolution — every one of those comes from the analyst's evidence or
  the user's explicit answer, never from this command's own judgment.
- Re-running this command (source artifacts changed upstream) re-surveys
  and re-confirms — it does not silently re-apply a stale prior survey.

## Approval gate

Same as any planning-phase stage, per `planning-protocol.md`: present the
survey's shape, approve/revise/stop. On approval, the writes in steps
4–8 happen as one pass; nothing is written before confirmation.

## Report (≤9 lines)

```
External tool: <name> (detected via <evidence>, or already recorded)
Goals mirrored: N -> planning/BUSINESS_GOALS.md
Segments seeded: N -> architecture.segments (owns_paths pending real code)
Tasks seeded: N (<N> blocked pending gaps, <N> ready) -> TASKS.md
Gaps found: N (<list, or "none">)
Planning stages: all marked skipped (external via <tool>)
Status: draft/approved
Next: run /agentic-harness:architect to begin implementation
```
